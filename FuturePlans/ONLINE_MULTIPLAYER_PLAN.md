# Online Multiplayer Plan

> **Status: PARKED** — like `LEADERBOARD_IDEA.md`, this is a post-launch item.
> Do not start implementation until the shell + 2 local games are live on the Play Store.
> Written now so the architecture decisions don't block us later.

## 1. What we're building

Two levels, in order:

1. **Phase A — "friend room" multiplayer** (Ludo first): 2–4 real humans in a private
   room with a 6-char code. No matchmaking, no accounts required. Lowest complexity,
   highest chance of shipping.
2. **Phase B — matchmaking + leaderboards** (ties into `LEADERBOARD_IDEA.md`):
   quick-match queues, ratings, global scores. Only after Phase A proves the netcode.

## 2. Our stack, honestly assessed

Current stack: **Kotlin shell + WebView games (HTML/JS) + no backend.**
Game logic lives in JS (Ludo). That shapes every choice below.

| Option | Verdict |
|---|---|
| **WebSocket relay (Node + ws / Colyseus on a small VPS)** | ✅ Recommended long-term. Authoritative-ish relay; JS games already speak JSON. Colyseus runs rooms in JS we could share with game code later. |
| **Firebase Realtime DB / Firestore** | ✅ Good Phase-A shortcut: room doc per game, no server code, free tier covers launch. Downside: cost/latency at scale, anti-cheat impossible via rules alone. |
| Google Play Games Services (real-time multiplayer) | ❌ Effectively deprecated for new games (Play Games v2 dropped realtime rooms). Avoid. |
| WebRTC data channels | ⚠️ P2P is nice but NAT traversal + signaling server = same work as a WS server, less control. |
| Self-built UDP/native | ❌ Massive overkill for turn-based Ludo. |

**Decision:** Phase A on **Firebase Realtime Database** (fastest to ship, zero ops),
revisit Colyseus/VPS when we add matchmaking or need sub-100ms turns.

## 3. Architecture (Phase A)

```
Shell (Kotlin)              Room hub (Firebase RTDB)               Game (JS/WebView)
──────────────              ────────────────────────               ─────────────────
create room ─────────────►  rooms/{CODE}:                          bridge.createRoom()
                             players: {seat, name, ready}          bridge.joinRoom(code)
join room  ─────────────►   state: {turn, dice, pieces...}
                            lastSeq, updatedAt                     game posts move:
seat/ready UI ◄───────────  moves/{seq}: {player, payload}         bridge.sendMove(json)
bridge = NativeBridge                                              game renders:
                                                                   bridge.onState(json)
```

- **Room code = 6 chars** (A–Z, no 0/O/1/I), created client-side, TTL 10 min idle.
- **State machine per game lives in the JS game** (Ludo already has it for bots);
  the relay only validates "is it your turn + valid seat" — a *thin arbiter*.
  Full server authority comes in Phase B.
- **Turn-based = forgiving netcode.** Moves are idempotent JSON with a seq number;
  clients replay missed moves on reconnect. No 60Hz sync needed anywhere in our
  catalog today.
- **Reconnect:** player disconnect → `onDisconnect()` marks seat "away" → 60s grace
  to rejoin (same seat), else bot takeover (we already have bot logic!) or room end.

## 4. Bridge additions (small, known pattern)

`NativeBridge` already passes settings and shell state into games. Add:

- `bridge.netCreateRoom(maxPlayers) → {code, seat}`
- `bridge.netJoin(code) → {ok, seat, players}` / `bridge.netLeave()`
- `bridge.netSendMove(json)` / `bridge.netOnState(cb)`
- Kotlin side = one `NetClient.kt` class wrapping Firebase RTDB, ~300 lines.

Ludo's menu gets a third option: **Play Online → Create room / Join room**.
Host sees the room code big on screen; guests type it. Standard, proven UX.

## 5. Identity & accounts

- **Phase A: no accounts.** Local "player name" set once in the shell + auto
  anonymous Firebase auth uid (invisible to user). Friend rooms don't need more.
- **Phase B (leaderboards/matchmaking):** the nationality/name/consent flow from
  `LEADERBOARD_IDEA.md` plugs in here. Play Account linking optional.

## 6. Cost & scaling reality check

- Firebase RTDB free tier: 100 concurrent connections — fine for launch friends &
  family; the paid jump is usage-based and cheap for turn-based traffic.
- One turn-based Ludo room ≈ a few KB/hour. Even 10k DAU playing one online game
  daily stays trivially affordable. The real bill arrives with matchmaking presence —
  hence Phase B gets its own doc.

## 7. Risks / gotchas to remember

- **WebView backgrounding:** Android may kill the WebView in background; all game
  state must live in the RTDB room, never only in JS memory (same lesson as
  settings sync).
- **Cheat surface:** with a thin arbiter, a rooted client can post impossible moves.
  Acceptable for Phase A (friend rooms = social pressure). Phase B must move turn
  validation server-side (Colyseus room logic or Cloud Functions).
- **Dice fairness for Ludo:** rolls must be generated by the *current player's*
  client but revealed with a seq; never re-roll on reconnect.
- **Play policy:** online interaction requires the "contains online features" data
  safety declaration + user block/report plumbing before public Phase A launch.
- **Battery:** RTDB listeners are cheap (single WebSocket), no polling. Ever.

## 8. Order of attack (when we get here)

1. `NetClient.kt` + bridge methods, no game changes (a shell debug screen proves rooms).
2. Ludo: online seat in menu, state sync, reconnect grace.
3. Polish: room code UX, "friend left" toasts, invite via Android share sheet.
4. Phase B doc: matchmaking queue, ratings (Glicko-lite), leaderboard union.
